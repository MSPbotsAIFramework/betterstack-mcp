## Product design

### Goals / Non-goals

**Goals (v1 — this ticket)**:
- An Agent can list and inspect BetterStack uptime monitors, and create/update/pause/delete them.
- An Agent can list incidents (open or historical, filterable by monitor/date/status) and acknowledge or resolve them.
- An Agent can see on-call schedules and who is on call (now or in a given window), to answer "who should I page".
- Per-tenant isolation: each MSPbots tenant supplies its own BetterStack API token through the platform's connector credential form (variant 1, "credential-style", per `ProductDocs/_connector-fields.md`); one tenant's monitors/incidents are never visible to another tenant's requests.

**Non-goals (v1, explicit scope cuts — see "Decisions made by DEV01" below for the reasoning)**:
- BetterStack Logs/Telemetry capabilities (log sources, log query/search, dashboards, alerts, explorations) are **not** built in v1. The ticket's one-line description only names monitors/incidents/on-call schedules — all Uptime/Incidents-API concepts; "via BetterStack Uptime and Logs" reads as naming BetterStack's product suite, not a request for log-query tools. Flagged as a non-blocking, documented assumption (see Open questions).
- Creating, editing, or deleting on-call schedules and rotations is out of scope; v1 is read-only for on-call (list schedules, list who's on call / upcoming shifts). Editing a rotation is a higher-risk, low-frequency action better done in BetterStack's own UI; it is not implied by "manage ... on-call schedules" strongly enough to build untested write paths for it in v1.
- Incident `reopen` and `escalate` actions are out of scope v1 (only `acknowledge`/`resolve`, which cover the common "triage" loop).
- Heartbeats, status pages, team/org/role management, usage/billing, metadata, and third-party integrations (e.g. the New Relic bridge) in the BetterStack API are out of scope — the ticket does not name any of them.
- No UI changes on the MSPbots platform: the connector credential form is the platform's existing generic "credential-style" connector dialog (variant 1); no new UI is being requested or built.

(Given/When/Then; the full Given/When/Then text for each is authoritative in `docs/tickets/PRD-21258.ac.json`, reproduced in the Test cases section below.)

- AC2: Get monitor by id — detail or not_found.
- AC3: Create monitor — validates required fields.
- AC4: Update monitor — including pause/resume via the `paused` field.
- AC5: Delete monitor — requires an explicit id, never a bulk filter; destructive.
- AC6: List incidents — filterable (monitor, resolved/acknowledged, date range), empty-result-safe.
- AC7: Get incident by id — detail or not_found.
- AC8: Acknowledge incident — idempotent.
- AC9: Resolve incident.
- AC10: List on-call schedules.
- AC11: List on-call schedule events ("who's on call", default or a specific schedule, optional time window) — not_found for an unknown schedule.
- AC12: Missing credential header → HTTP 401 listing the required header name(s), no tool executes.
- AC13: Invalid/expired token → structured `unauthorized` error, not a 500 and not a silent empty result.
- AC14: Upstream rate limiting or 5xx/timeout → structured `rate_limited` / `upstream_error` with `retryable=true` after the service's own limited retry budget is exhausted.
- AC15: Concurrent requests from different tenants never cross-contaminate credentials or data (no module-level cache, no global credential variable).
- AC16: Logs never contain the credential header value or the full upstream response body.
- AC17: `/health` returns 200 independent of whether the BetterStack API is reachable.

## Tech design

### Conclusion

Build `betterstack-mcp` as a new Python/FastMCP service per `vendor-mcp-development-sop.md` main line A (clean-room implementation against BetterStack's public REST API, no forking/mirroring of any open-source BetterStack MCP). Single credential header (`X-Betterstack-Api-Token`) covers both the Uptime/Incidents API and the on-call endpoints, since BetterStack's own docs describe one Bearer-token scheme (Global or team-scoped) across these resources. 11 tools across 3 resource domains (monitors, incidents, on-call) keep the service well under the 20-tool guideline while covering everything the ticket names.

### Data & API contract

**Credential header** (declared in `README.md` per SOP §3.1):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Betterstack-Api-Token` | Yes | BetterStack API token (Global API token, or a team-scoped Incidents/Uptime API token) — forwarded as `Authorization: Bearer <token>` to BetterStack | BetterStack dashboard → Settings → API tokens |
| `X-Betterstack-Base-Url` | No | Override the Uptime/Incidents API base URL; default `https://uptime.betterstack.com/api/v2` | — (for self-hosted/region edge cases; BetterStack is single-region SaaS today, this is forward-compatible headroom consistent with how other connectors expose an optional base-URL override, e.g. IT Glue/Datto in `ProductDocs/_connector-fields.md`) |

Missing `X-Betterstack-Api-Token` → HTTP 401, body lists the required header name (SOP §3.2).

**Base URL note for the dev leg**: BetterStack's own docs reference both `uptime.betterstack.com/api/v2` and `incidents.betterstack.com/api/v2`/`v3` for what appears to be the same backend (BetterStack merged the "Better Uptime" and "Logtail" products under one brand). Default to `https://uptime.betterstack.com/api/v2` (confirmed working for monitors and on-call endpoints by both official docs and a web search cross-check on 2026-11-02) and verify empirically against a live token before locking it in; if `incidents.betterstack.com` turns out to be required for a specific endpoint, that confirmation belongs in the dev leg's self-test notes, not a guess here.

**Tools** (`<vendor>_<verb>_<resource>` naming per SOP §2.8; `limit` default ≤50 / hard cap ≤200 per §2.5; read tools annotated `readOnlyHint=true`, delete annotated `destructiveHint=true`, ack/resolve annotated `idempotentHint=true`):

1. `betterstack_list_monitors(url?: str, pronounceable_name?: str, limit?: int=50, cursor?: str)` → `GET /monitors` (`page`/`per_page` mapped from `limit`/`cursor`). Returns `{data: [{id, url, pronounceable_name, monitor_type, status, paused, check_frequency}], has_more, next_cursor}`.
2. `betterstack_get_monitor(id: str)` → `GET /monitors/{id}`. `not_found` on 404.
3. `betterstack_create_monitor(url: str, monitor_type: str, pronounceable_name: str, check_frequency?: int)` → `POST /monitors`. `invalid_argument` on 400/422.
4. `betterstack_update_monitor(id: str, paused?: bool, check_frequency?: int, pronounceable_name?: str)` → `PATCH /monitors/{id}`. `not_found` on 404, `invalid_argument` on 422.
5. `betterstack_delete_monitor(id: str)` → `DELETE /monitors/{id}`. Single explicit id only — no filter-based bulk delete (SOP §2.7). `destructiveHint=true`.
6. `betterstack_list_incidents(monitor_id?: str, resolved?: bool, acknowledged?: bool, from_date?: str, to_date?: str, limit?: int=50, cursor?: str)` → `GET /incidents`. Returns `{data: [{id, status, started_at, acknowledged_at, resolved_at, acknowledged_by, resolved_by}], has_more, next_cursor}`.
7. `betterstack_get_incident(id: str)` → `GET /incidents/{id}`. `not_found` on 404.
8. `betterstack_acknowledge_incident(id: str)` → `POST /incidents/{id}/acknowledge`. `idempotentHint=true` — acknowledging an already-acknowledged incident is a success, not an error.
9. `betterstack_resolve_incident(id: str)` → `POST /incidents/{id}/resolve`.
10. `betterstack_list_oncall_schedules(limit?: int=50, cursor?: str)` → `GET /on-calls`. Returns `{data: [{id, name}], has_more, next_cursor}`.
11. `betterstack_list_oncall_events(schedule_id?: str="default", from_date?: str, to_date?: str)` → `GET /on-calls/{schedule_id}/events` (no upstream pagination per BetterStack's docs; this endpoint returns all matching events, so the service applies its own `limit`/truncation per §2.5 if the window is large). Returns `{data: [{event_id, user_name, starts_at, ends_at}], has_more}`. `not_found` if `schedule_id` doesn't exist upstream.

**Error envelope** (SOP §4.2, exact vocabulary — `not_configured` is not used here since the middleware intercepts missing-Header before any tool runs):

```json
{"error": {"code": "not_found", "message": "Monitor 12345 does not exist", "retryable": false}}
```

`code` ∈ `{unauthorized, not_found, invalid_argument, rate_limited, upstream_error}`, mapped from BetterStack's HTTP status (401/403→`unauthorized`, 404→`not_found`, 400/422→`invalid_argument`, 429→`rate_limited`, 5xx/timeout→`upstream_error`). Empty list results are a normal success, never `not_found` (SOP §4.2, AC1/AC6).

**Backward compatibility**: this is a new service, nothing to be compatible with yet. Forward-looking: new optional filter kwargs can be added to any `list_*` tool without breaking existing callers (SOP §13: adding an optional parameter is a compatible change).

### Key flow / sequence

```
Agent -> Gateway -> betterstack-mcp /mcp (Header: X-Betterstack-Api-Token)
  middleware: read header -> ContextVar; missing -> 401, stop
  tool (e.g. betterstack_list_incidents):
    api_client.get("/incidents", params=..., token=ContextVar.get())
      -> BetterStack API
      <- 200 {data: [...], pagination: {...}}
    map response -> trimmed fields, has_more/next_cursor
    return JSON string
  finally: ContextVar.reset()
```

Write path (`betterstack_acknowledge_incident`) is the same shape with `POST` and no response trimming beyond the normal field selection.

### Non-functional

- **Idempotency & concurrency**: no local state at all (stateless HTTP, SOP §1.3); `acknowledge`/`resolve` are naturally idempotent at the BetterStack API level (re-acknowledging an already-acknowledged incident succeeds, confirmed by BetterStack's own incident-state model: Started → Acknowledged → Resolved, re-posting the same transition is a no-op, not an error — AC8/TC-BS-016 verifies this). `delete` is not idempotent by nature (second delete → `not_found`, which is treated as success-shaped information, not a crash) but is never retried automatically for that reason — only read and genuinely-idempotent calls get the automatic 429/5xx retry (SOP §5); `create`/`update`/`delete`/`acknowledge`/`resolve` do not get requeued without the caller re-invoking the tool, since blind retry of a POST side effect risks duplicate action (e.g., double-create).
- **Performance**: `limit` defaults to 50 / caps at 200 per list tool (§2.5); single-call budget < 120s (§5); connection pooling via one shared `httpx.AsyncClient` per request lifecycle, not per-call.
- **Security**: credentials only from `X-Betterstack-Api-Token` (never an env-var fallback, SOP §3.1); request-scoped `ContextVar`, reset in `finally` (§3.3); no cross-request caching of tokens, derived data, or org info (§3.4); error messages never echo the raw upstream body (§4.2) or the token (§6); DNS-rebinding protection off (service is internal-only, SOP §7).
- **Multi-tenant isolation**: the entire isolation guarantee is architectural, not per-feature — one container serves many tenants concurrently, each request carries its own token, nothing is shared or cached across requests (AC15/TC-BS-025 is the concrete test of this).
- **Observability**: structured logs with request-id, tool name, redacted arg summary, BetterStack status code, duration, error `code` (§6); never the token or full response body (AC16/TC-BS-026).

### Risks & dependencies

- **Risk**: BetterStack's docs are inconsistent about the exact base host (`uptime.betterstack.com` vs `incidents.betterstack.com`) for a couple of endpoints. Mitigation: dev leg confirms empirically with a live call before locking `config.py`'s default; low risk since both hosts are documented as valid for most of these endpoints.
- **Risk**: on-call "list events" endpoint (`GET /on-calls/{schedule_id}/events`) is documented as unpaginated (returns all matching events) — a schedule with a very long history could return a large payload. Mitigation: the service applies its own client-side truncation to the §2.5 20,000-character / `limit` budget regardless of what BetterStack returns, with `has_more=true` when truncated.
- **Dependency**: none on other tickets or repos — greenfield, single-repo, no gateway change (confirmed no need to touch `mcp-service-gateway`, so this does not route to Leo Yang per `mcp-track.md` rule 5).
- **Dependency**: a real BetterStack token is needed only for the one manual end-to-end case (TC-BS-028); absence does not block merge or INT publish.

## Decisions made by DEV01

(Per `mcp-track.md` 2.4 — a new MCP's own tradeoffs must leave a paper trail: choices made without a human to ask, for a brand-new MCP's first version.)

- **Scoped v1 to Uptime/Incidents-API capabilities only (monitors, incidents, on-call); excluded BetterStack Logs** — because the ticket's one line names only monitor/incident/on-call management; "Logs" in "via BetterStack Uptime and Logs" reads as the product-suite name. Alternative not chosen: build a parallel set of log-query tools speculatively — rejected because there's no concrete Agent task named for it, and SOP §2.1 says build capabilities Agents actually need, not every available endpoint.
- **Monitors get full CRUD (list/get/create/update/delete), on-call is read-only** — "manage monitors" reads as configuring them (not just viewing), while "manage ... on-call schedules" is more naturally read as visibility ("who's on call") for a chat Agent; editing rotations is a rarer, higher-blast-radius action better left to BetterStack's own UI for v1. Alternative not chosen: read-only monitors too — rejected, doesn't match "manage".
- **Incidents get acknowledge/resolve only, not reopen/escalate** — covers the common triage loop (ack → resolve) in the fewest tools; reopen/escalate are additive later if asked for. Alternative not chosen: all four incident actions in v1 — rejected to keep the v1 tool count minimal per SOP §2.1 ("fewer, sharper tools beat many overlapping ones").
- **Single credential header `X-Betterstack-Api-Token`, no separate header for the Logs API** — consistent with excluding Logs from v1, and BetterStack's own docs describe one Bearer-token auth scheme across Uptime/Incidents/on-call.
- **Default base URL `https://uptime.betterstack.com/api/v2` with an optional `X-Betterstack-Base-Url` override** — matches the host most consistently confirmed by both official docs and an independent search for the monitors/on-call endpoints; the override header is forward-compatible headroom in case `incidents.betterstack.com` turns out to be required for a specific endpoint during implementation (see Tech design § Risks).

To change any of these, say so in a comment and move the ticket back to `5b - ready for groom`.

### Interpretation call: TC-BS-007 "missing" url

`betterstack_create_monitor`'s `url` parameter is a required MCP tool parameter with no default (confirmed in the `tools/list` schema: `"required":["url","monitor_type","pronounceable_name"]`). An entirely omitted argument is rejected by MCP protocol-level JSON-schema validation before our tool code ever runs, so it can't exercise our own `invalid_argument` envelope. TC-BS-007 is implemented by passing `url=""` (present but empty) and asserting our own validation returns `invalid_argument` without calling the upstream API — this is the only way to test "the service validates this required field" as opposed to "the MCP transport validates its own schema." No AC or test text was changed; this is a note on how the case was executed, not a change to what it tests.
